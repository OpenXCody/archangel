# ARCHANGEL

US Manufacturing Workforce Intelligence Platform at o-10.com

## Quick Context

Archangel is a workforce map of US manufacturing, filled out in depth one focus area at a time, starting with Austin, TX. People explore **Industries → Companies → Factories → Jobs → Careers → Skills** on a map and through entity pages; seekers track skills and apply to jobs, employers post jobs and read applicants, admins load and correct data.

## Tech Stack

- **Frontend**: React 18, TypeScript, Vite, Tailwind CSS, shadcn/ui
- **State**: Zustand (UI), TanStack Query (server)
- **Backend**: Express.js, TypeScript, Drizzle ORM
- **Database**: PostgreSQL (Neon), with `pg_trgm` for search
- **Maps**: MapLibre GL JS + MapTiler (free tier)

## Theme and colour

Two themes, dark (default) and light, switched in settings (`/settings`, Appearance, which is shown signed out too) and kept per browser (`client/src/lib/theme.ts` sets `data-theme` on `<html>`; `client/index.html` applies it before first paint). Each theme is set by hand; neither is the other inverted. Every colour comes from the eleven tokens in the `:root` blocks of `client/src/styles/globals.css` (the token file), exposed as Tailwind classes in `tailwind.config.ts`:

| Token | Classes | Use |
|-------|---------|-----|
| `--bg` | `bg-bg` | The page |
| `--surface`, `--surface-hover` | `bg-surface`, `bg-surface-hover` | The only raised fill (inputs, the map's panel and controls); hover on rows and tiles |
| `--line`, `--line-strong` | `border-line`, `border-line-strong` | Hairlines; the edge of an input, a secondary button, an unselected tile |
| `--text-1`, `--text-2`, `--text-3` | `text-text-1`, `text-text-2`, `text-text-3` | Headings and values; secondary text; meta |
| `--accent` | `outline-accent`, `border-accent`, `bg-accent/[0.06]` | See below |
| `--inverse-bg`, `--inverse-text` | `bg-inverse-bg`, `text-inverse-text` | Primary buttons, the selected segment |

There are two surface levels and no third grey. Beside the eleven the file holds `--danger` (errors and destructive actions; there is no success or warning colour: a confirmation is ink), `--logo-backing`, `--mask` and the map's five (`--map-land`, `--map-land-other`, `--map-water`, `--map-border`, `--map-road`). The accent is for focus rings (`outline: 2px solid var(--accent); outline-offset: 2px` on every interactive element, one global rule), the selected map region, a focus area's outline, a hiring factory's ring, the Atlas's overlaid career and the "Viewing as" sign: never a heading, body text or a button's fill.

Never name a colour outside the token file: `npm run lint` fails on a hex value, a colour function, a palette class, `white` or `black`, and on the names the tokens replaced, in every client file (`scripts/check-theme-colors.mjs`). `tests/unit/theme.unit.ts` holds the three inks to 4.5:1 on both surfaces. The `theme-color` tag in `client/index.html` and the manifest's two colours are copies of the dark `--bg`, held equal by the lint. The app is monochrome: kinds of thing (company, factory, career, skill) are told apart by their word (the kind above a page's name, the heading over a list) and a company by its logo, not by hue. The map paints only from tokens: `layers.ts` reads them from the page when the map is built and holds no colour; the map is recreated when the theme changes.

## Coverage and focus areas

**What counts as manufacturing.** A factory makes a product on its own site. Construction does not count, nor does material mixed or cast for a building site: ready-mix concrete (NAICS 32732), concrete pipe, brick and block (32733), other concrete products (32739) and asphalt paving mixtures (324121) are left out and must not be loaded again (`0038_remove_construction_materials.sql` removed them; `NOT_COVERED` in `scripts/build-employers-sql.mjs` refuses them). Cement factories (32731) are in, along with lime, gypsum, glass, brick and roofing. Puerto Rico is out (`0029`).

Two separate ideas (`shared/scope.ts`):
- **Coverage** is which rows the public API returns: the whole country (`SCOPE.stateCode` is `null`, so the helpers in `server/lib/scope.ts` are no-ops). Every public GET still builds its conditions from those helpers, so narrowing later is one setting.
- **Focus areas** (`FOCUS_AREAS`) are regions being filled out in depth. The first is Austin, TX, bounded by its five metro counties (`client/public/data/areas/austin.geojson`). The map draws each as a geofence; `/api/map/areas/:id/overview` gives it the same panel data a state has.

The map opens on the continental US. A focus area is somewhere to go, not a limit on what exists.

Pins carry a tier: 2 featured employer (`companies.featured`), 1 established company (five or more factories nationwide), 0 other. `companies.domain` is used for logos.

## Depth and sources

A factory can carry how many people work there (`workforce_size`, with `workforce_year`, `workforce_source`, `workforce_note`), what it makes (`products`), the year it opened (`opened_year`) and its `status` (`operating` or `under construction`). `curated` marks a factory whose facts were written from sources, by a research file or by an admin. A company can be part of another (`parent_company_id`), has headquarters as city, state and country, and people in a state (`company_state_headcounts`: loaded from files and shown, with no editor). Sources are rows in `external_references`: `source = 'CURATED'`, one per source address, and `'EPA_ECHO'` for a factory's EPA registry id. `server/lib/sources.ts` reads them and the API gives them (`sources` on a factory's and a company's record), but a page states the fact and never where it was read: no source links, no publisher's name, no notes about a figure, on any public screen (an industry page says only which of its figures are official and their year) (`components/entity/RecordFacts.tsx` draws a factory's facts). Where a fact came from is for the data and for Admin Tools. A curated factory's name and address are shown as written; `formatFactoryName` only reshapes names that shout.

Curated employers and factories arrive as research files in `data/employers/`: five Texas files by sector, `texas-osha-additions.json` (Texas factories of 300 or more people found in OSHA Form 300A filings) and `us-largest-plants.json` (ranked on the same filings). They load through migrations generated by `scripts/build-employers-sql.mjs` (`0040_texas_employers.sql`, `0041_largest_plants.sql`): the files as JSON plus the functions in `scripts/employers-loader.sql`. The loader cannot see production, so it decides everything in SQL when the migration is applied and writes each decision to `load_log` (`look = true` on the lines to read). A company is found by exact name or alias only, in any letter case; rows found under several names are merged and their names kept as aliases. A factory is placed on the row that already is that factory (by company, name and distance) or added, and never deleted. A second load keeps the fuller fact. Our corrections to a research file go in `data/employers/corrections.json`, never in the file. A new file is checked (`--check`) and rehearsed on a copy of production (`--rehearse`, which undoes itself) before its migration is generated. `scripts/ingest/README.md` has the contract, the loader's rules and the steps.

## Intake

Large sources come in through `scripts/ingest/run.mjs`, outside the deploy: an adapter in `scripts/ingest/sources/` reads the file, `stage` keeps what the source said (`intake_records`), `resolve` decides which factory each record is (`intake_links`; by the source's id in `external_references`, then by the employer loader's rules), `apply` writes ids and facts, `undo` takes a run back, `rehearse` does it all in a transaction that is rolled back. It refuses a database that is not local unless `--yes-this-database <host>` names it. On production it is run by hand from GitHub (`.github/workflows/ingest.yml`: Actions, Ingest, with the repository secret `INGEST_DATABASE_URL`; modes `rehearse`, `apply`, `undo`; the report is saved as an artifact; the source `counties` runs `scripts/geo/assign-keys.mjs` the same way, without an undo). The first adapter is `epa-echo` (the EPA's ECHO Exporter, read by registry id: it fills only empty facts and adds no factory).

A source's id names one record (`external_refs_identity_key`; `CURATED` rows are citations and stand outside it; two rows that already carried one id are marked `duplicate` and are factories to merge). What a staged record writes to a factory is `intake_apply_record` in the database, called by the runner and by Admin Tools; `intake_fact_wins` is the one rule: an admin's value is never replaced, an empty fact is filled, a source that only fills stops there, otherwise the higher rank and then the newer value wins. `fact_sources` says where each of a factory's facts came from, `intake_changes` what each run changed, `record_merges` which record was merged into which (`record_now` follows it). Two rows that are one factory are merged by the database (`plant_merge`, migration 0051; `scripts/plant-merge.sql`): the kept row (`plant_keeps`: curated, then a headcount, then placed in a county, then more facts, then older) keeps its name, company, place and facts and takes the other's where its own are empty, everything attached moves, and the merge is written to `record_merges` and `load_log`. A curated factory is never merged into one that is not. `plants_apart` holds pairs an admin said are two factories. `GET /api/factories/<old id>` answers 301 to the factory kept, and the factory page follows it. `load_log` is also where a run writes its decisions (`run_id`, `source_id`, `entity_id`, `evidence`). A run never deletes a factory or a company. Bulk data no longer goes in a migration. `scripts/ingest/README.md` has the design: the tables, the life of a run, matching, ranking and the adapter's contract.

## Job postings

Open jobs come from employers' own public postings, every day, with nobody's hand in it. `data/employers/boards.json` has one line per employer (the company as our data names it, the hiring system, the board) and, for an employer left out, why (`refused`, `not verified`, `no adapter`); adding an employer is a line, never code. One adapter per hiring system (`scripts/ingest/postings/systems/`: Greenhouse, Lever, Ashby, Jibe, Oracle, Workday, SuccessFactors) turns a board into postings a page at a time. Everything asked of an employer's site goes through `scripts/ingest/postings/fetch.mjs`: one user agent that says what it is, the host's robots file read first and obeyed, a pace per host, and the stop rule: a 401, 403, 429, a challenge page or a reset ends that employer for the run (a 429 or a reset ends the platform), is written to the run, and nothing is asked again with other headers. An employer whose site refuses stays out of the registry with the reason beside it.

**Reading** (`scripts/ingest/postings/read/`: `loadVocabulary`, `readPosting`): rules over the curated files in `data/`, no model, no network. A posting is kept only when its title is one of the 156 careers (by title, another name, or a close match the reader is sure of; a wrong career is worse than a missed posting); a kept one is read for its level, its places, the skills and makes it asks for (each match says what it matched on), its requirements (years, schooling, certificates, clearance, citizenship, shift, type: what is asked, never what is only preferred) and its pay. `tests/fixtures/postings/gold.json` is 480 hand-labelled postings and `tests/unit/postings-read.unit.ts` holds the reader to its measured figures as a floor. A change to what a career or a skill is called is a change to `data/`, never to the reader.

**What is kept is facts and a link, never the employer's wording**: the text is read in the runner's memory and let go; staging (`intake_records`) holds the posting's id, a hash and the reading. A posting that is not one of our careers leaves no row (`posting_passes` notes only that its text was read, so it is not asked for again).

**A posting is a job**: a row in `jobs` with `source` and `source_id` set, `level_word`, `level_rank`, `requirements` (jsonb, only the keys that were said), `job_makes`, `last_seen_at`, and `undated` where the feed gives no date (the page then says "Listed", not "Posted"). The runner (`node scripts/ingest/run.mjs postings`; sources of kind `job`, `postings-<slug>`) orchestrates and the database decides (migration `0054`): `posting_decide` says which factory and career each posting is, `posting_resolve` keeps the places that wait, `posting_apply` brings the jobs in line, `intake_undo_run` takes a run back. The factory is the company's factory in the city the posting names; of several, the one whose address or name the posting's words carry, else the one with the most people, else the factory merge's order (flagged); with none in the city, the company's nearest within 10 km (flagged); otherwise no job is written and the place waits in Admin Tools (Data leads to "Postings with no factory" while some wait, `?tab=data&postings=places`, `components/admin/Postings.tsx`: point a place at a factory, and every posting naming it follows, or leave it). A factory is never added and a state never guessed. A company the registry names that we do not list is logged and its board is not read. One outside id (`<posting id>@<place key>` in `external_references`, entity type `jobs`) is one job; one posting is one job at a factory.

**It tends itself.** A posting is gone only against a listing read to its end (`counts.complete` on the run): after two such listings without it the job is closed ("No longer on the company's careers site"), and it reopens if it returns; a listing that was refused, unreachable or cut closes nothing. A job from a source expires 14 days after the last complete listing that included it, so the lists empty by themselves if runs stop. A run never deletes a job. Workday is asked sparingly: 300 requests a run across all its boards, four seconds apart (`budget` in `systems/workday.mjs`), the boards whose complete listing is oldest first, a cut listing taken up where it stopped; where a text costs a request the reader is asked about the title first.

It runs from GitHub (`.github/workflows/postings.yml`: daily at 09:23 UTC and by hand, modes `apply`, `rehearse`, `undo`; the repository secret `INGEST_DATABASE_URL`; without it the run says so and ends green; the report is the run's artifact; under half an hour a day). Admin Tools, Data, lists each employer's latest run. `scripts/ingest/README.md`, "Employers' job postings" and "Reading a posting", has the design.

A company's version of a career is not written from postings yet (`company_careers.origin = 'source'` is kept for it; `job_skills` and `job_makes` by company and career are what it would be summed from).

## Geography and industry keys

A factory joins to public statistics through keys on its row (migration `0044`): `lat` and `lng` (generated by the database from the text `latitude` and `longitude` the app reads and writes, so they cannot disagree), `county_fips`, `cbsa_code` (its metro area) and `naics` (the 2022 six-digit code `primary_naics` means, when it means exactly one; `primary_naics` is kept as stored). The reference tables are `counties`, `metros`, `naics` (manufacturing, sector to national industry, each code with its parent; the 3-digit level is the 21) and `naics_concordance`, loaded from `data/geo/` and `data/industries/naics-*.json` by the generated migration (`scripts/build-geo-sql.mjs`; a unit check fails when the two disagree).

A trigger (`factories_keys`) keeps `naics` in step with `primary_naics` and clears the county when coordinates change. The county is written by `scripts/geo/assign-keys.mjs` (point in polygon against the Census Bureau's county boundaries, which stay outside the repository): a dry run unless `--apply`, refuses a database that is not local without `--remote`, safe to repeat, run after every load that adds or moves factories. A factory whose coordinates fall in another state than the one it is filed under gets no county and is listed. `scripts/ingest/README.md` has the steps. Any statement that inserts into `factories` names its columns: `lat` and `lng` cannot be written.

Official statistics for manufacturing as a whole are also kept by county (`industry_county_stats`, from the same QCEW adapter: `data/industries/qcew-<year>-counties.json`). A factory's page says its county's figure in one sentence under the address (`components/entity/CountyLine.tsx`, `GET /api/map/factories/:id/county`): a figure about the county, never the factory, with no source named, and nothing when none is published. The map's panel does not carry it.

## Employers: jobs and applicants

`/employer`, called **Your jobs** in its tab, heading and back links, is the list of a person's companies and jobs; the job form takes the page over from the address: `?post=1` (new), `?copy=<job id>` (another like an existing job), `?edit=<job id>` (change one; `&from=job` returns to the job's page). One form does all three: `components/jobs/JobForm.tsx`. A job's company, factory and career are fixed once posted. A job's edits, its applicants and the form's checks are in `client/src/lib/employerJobs.ts`; posting and closing in `lib/jobs.ts`.

On a job's page a person who manages it sees the company's view first (state, Edit, Post another like this, Close or Delete, then applicants) and the listing below it, with skills unmarked. Applicants are a compact list (`components/jobs/ApplicantList.tsx`), filtered by stage; a row opens to the applicant's skills against the job's (held, learning, missing), their note and contact, the private note and the stage. Hired and Declined take a confirmation and can be moved back to a working stage; Withdrawn is the applicant's and the company cannot change it. A job with no applications can be deleted; one with applications can only be closed.

A job that came from the company's careers site (see "Job postings") is kept in step with it and is not managed here: it has no description and no applicants, Apply opens the company's own page in a new tab with one line beside it saying whose careers site that is (`components/jobs/SourcedJob.tsx`), a member sees it read-only, and `PATCH`, `DELETE` and `apply` on it answer 409 or 400. Your jobs says how many of a company's open jobs come from its careers site (`listedJobs`).

A person finds their company on `/employer` by name (`GET /api/employer/companies`, `server/lib/companySearch.ts`): tolerant of spelling, spacing, "&" and the legal form, name matches only, the closest names when nothing matches. A company or a factory that is not in the data is asked for there (`company_requests`, `server/routes/companyRequests.ts`); an admin answers it on the Access tab ("Companies and factories to add"), and answering a company request gives the person access. After sign-in a person with a waiting request lands on `/employer`.

The job form keeps what is typed in the browser (`client/src/lib/jobDraft.ts`, one draft per person and form) until it is posted, saved or started over. The factory is chosen with `components/jobs/PlantPicker.tsx`. One person posts at most 30 jobs an hour. Applicants can be searched by name (above eight) and exported as CSV from the browser (`applicantsCsv` in `employerJobs.ts`).

Career search (`server/lib/careerSearch.ts`, behind `GET /api/occupations`) reads titles and `occupation_aliases`, with word order, plurals and level words set aside, and falls back to the closest titles. Everyday names are curated in `data/careers/aliases.json` (see "Careers"). A row found by another name carries `alsoCalled`, and the career picker says it.

## Seekers: skills and reach

`/me` is called **Profile**: that word stands above the person's name. Applications come first, and only when there are any; then Goals, then Skills, with the person's own skills before the suggested ones.

A skill is marked where it is listed. Wherever skills are shown as a path they are **tags** (`SkillTag` in `components/path/`): the mark (`SkillHeldToggle` in `components/account/SkillStatusButton.tsx`), which sets the skill held or clears it in one tap, then the name, which opens the skill's page. Learning is set on the skill's page. A tag has no fill: a held skill is a filled check in full ink, one being learned the half mark in the same ink, the rest an open circle and secondary ink. The change is optimistic (`useMarkSkill` in `client/src/lib/seeker.ts`), so every figure follows at once. How much is held is always the same ring (`ShareRing` in `components/path/HeldShare.tsx`): bright for held, dimmer for learning, which is never counted in the figure. On a career's Atlas view the ring is the plate's centre, and the groups carry no figure of their own. A page gets the person's marks from `useSkillMarks()` and passes them down; with none (a visitor, someone here to hire) the same parts draw no marks and no progress.

On `/me` a person's skills stand under their domain, each group under its line, which says how much of the whole group is held ("Shop basics · 1 of 3"); a skill is taken off with its mark and its tag stays, quiet, until the page is left. A goal's next skills are named under their level.

Careers within reach (`GET /api/me/careers/reach`, shown on `/me` under Goals as "Within reach"; civilian careers only, as are suggested skills and goals): careers with a path (`occupations.path_status` is set) of at least five skills of which the person holds at least one, ranked by the share held, each with the next skills to pick up, lowest level first, and how many jobs are open for it (`openJobs`, on the page a link to Jobs). "Within reach" is one rule, `withinReach` in `shared/reach.ts`: a third or more of a path of five skills or more. Profile lists under those words only the careers that pass; when none does it lists the closest ones under "Closest careers" (`reachOrClosest`). Held skills count fully; a skill being learned counts as half for the order only, never in the figure. Careers already chosen as goals are left out; goals carry their own `next` skills (`GET /api/me/goals`). A next skill and a suggested skill each carry their `level`.

A new account with nowhere to return to lands on `/me`. With no goal, skill or application the page is two doors, set alike: "Start with a career" (search, or one tap on a career that has a path) and "Start with what you have done" (`components/me/ServiceDoor.tsx`); either fills the page. The second is for a person who served: a search of military careers by code, title or service (`GET /api/occupations?military=1&search=`, which reads the header's rule with every code counting), and choosing one marks every skill of its path held in one write (`POST /api/me/careers/:id/held`, 400 for a civilian career) and says "Marked 26 skills held. Undo". Undo (`POST /api/me/careers/:id/held/undo { at, added, raised }`) touches only the rows that write stamped: a skill held before, marked again since, or given a make since, stays. Every tap of the visit keeps its own Undo. Nothing is stored about which career it was: the person's skills are the record. On a Profile that has goals or skills the door is one line at the end of Skills (its list opens above the field when there is no room under it: `flip` on `CareerPicker`). It is drawn for a seeker only. Suggested skills (`GET /api/me/skills/suggested`, under Skills on `/me`) are the skills of the person's goals, then of careers within reach, none already on their list; one tap on the mark adds one, another takes it off, and the list holds still while it is marked (`useSuggestedSkills` in `lib/seeker.ts` is not under the skills key). Removing a goal leaves "Removed X. Undo" in its place until the page is left.

`/jobs` is two fields and a list: what (`?q=`, every typed word matched in the title, company, career, shift, city or state: `server/lib/jobSearch.ts`) and where: `?state=`, or `?near=<lat>,<lng>&place=<name>&within=<miles>` (50 by default), chosen in the Where field (`components/jobs/JobPlaceFilter.tsx`: a ZIP code or town through `lib/geocode.ts`, or a state; a state select only when there is no map key). The browser is never asked for the person's location. A career is narrowed to by a link (`?career=<id>`) and named in the line above the list. A company's, a factory's and a skill's page link to all of their open jobs the same way (`?company=`, `?plant=`, `?skill=`). The list is read a page at a time (`total`, `limit`, `offset`) in one order, `jobsInOrder()`: the newest day first, and within a day one job of each company in turn. A row says pay only where the job states it. With no open job anywhere the page has no fields.

## Careers

Careers are curated: 156 real jobs at the grain of a trade or role, in `data/careers/catalogue.json`, each with one home domain (`occupations.home_domain`, a `skill_domains` slug), one or two sentences, and up to three `leadsTo` links to the next rung (`occupation_links`: from, to, position; no chain comes back on itself). Finer titles (tasks, single machines, products, employer or program names, certification levels) are kept as other names of the career they belong to (`was` in the file, `occupation_aliases` in the database). `scripts/build-careers-sql.mjs` (`--check`) generates `0046_careers_catalogue.sql`, which decides in SQL on the database it meets and writes each decision to `load_log` (load `careers-catalogue`; `look = true` on the lines to read). It keeps the row already carrying the title, else the one with the most skills; moves goals, jobs, factory and industry links and other names to it; keeps one path (the title row's own when it has ten skills or more, else the fullest row's); creates a career that is not stored; leaves a career the file does not name alone; and does not remove a title that has a job with applications or is somebody's goal. `data/careers/industries.json` and `aliases.json` name only catalogue titles and load through `scripts/build-career-lists-sql.mjs` (`0047_career_lists.sql` first, `0056_career_lists_2.sql` now), which makes `industry_occupations` exactly the list for the catalogue's careers. `aliases.json` can also say a name is not a career's (`not`): the lists migration deletes that name from that career in `occupation_aliases` and writes `name removed` to `load_log` (load `career-lists`, which also has each name added and, with `look = true`, each left because another career has it), and the posting reader does not read it, whether it was an everyday name or a title in the catalogue's `was`.

A career's path is decided in `data/careers/paths.json`: every career of the catalogue by title, with its skills by their catalogue names, a `basis` (where the path was read from), a `why` beside any skill a reader would question, `lacks` (what the catalogue has no skill for; not loaded) and `weakLinks` (the ladder links across which under a third of the lower career's skills carry, each with its reason). A path names skills and sets no level. `scripts/build-career-paths-sql.mjs` checks it (`--check`; `--report` prints the figures: sizes, skills on no path, the share each ladder link keeps) and generates `0052_career_paths.sql`, which decides in SQL and writes to `load_log` (load `career-paths`): each career of the file gets exactly the file's skills and becomes a draft; a path a person approved is left exactly as it is and the log says what the file would change; a career or a skill name that is not stored is said and skipped; a career the file does not name is left alone. A draft path an admin edited is replaced: approve a path to keep it. A change to the paths is a change to the file and a new generated migration (the builder's last argument is the output), and `tests/unit/paths.unit.ts`, which names the latest, is pointed at it.

A career's page says its home under the description, a quiet link into the Careers list narrowed to it, and stands on its ladder: where it comes from before the first level, where it leads after the last. The ladder names three careers on a side and keeps the rest behind "N more"; a career whose path is not written yet is drawn as one node between the two (`LadderAlone`).

## A company's version of a career

The catalogue holds the standard career; a company says how it is done there as changes against it (migration `0053`): `company_careers` (one per company and career, `origin` `member | admin | source`), `company_career_skills` (`change` is `added` or `left_out`) and `company_career_makes` (the makes it runs, for a skill on the version's path). A version is a difference, never a copy: it is read as the career's `occupation_skills` without the skills left out and with the ones added (`server/lib/versions.ts`), so it follows the standard, and no trigger keeps it in step. A stored change that no longer applies is not read and is dropped at the version's next save. A version with no changes still says the company hires for the career. Makes hang on the version, not on a factory. As a title it reads "Boeing CNC Operator" (`versionTitle` in `shared/versions.ts`, which drops a legal form from the company's name); in running text "CNC Operator at Boeing". **Nothing is ever written for a real company by us: no seed, migration or sample says what one runs** (a unit check holds it); the local sample's made-up companies get a few through `server/scripts/seed-versions.ts`. A generated migration that merges careers or skills in SQL does not carry versions (only `recordMerge.ts` does): one that folds a career with versions must move them itself.

The career's page stays the standard and lists the companies with a version under Companies; each row opens `/occupations/:id?at=<company id or slug>`, the same page drawn by `components/entity/CareerVersionView.tsx`: the company's mark before the name, one line leading to the company and back to "Standard <career>", the path from the same parts, "Added" on a skill the company adds, one line under the path that says how many skills are left out and opens them, and the makes the company runs on a tag's second line (one the person has run is brighter, never another colour). A seeker's marks and progress count the version's skills. A company's page lists its careers, versions first. A job whose company has a version of its career links it (`hasVersion`), and the job form and `POST /api/jobs` start from the version's skills. The Atlas takes `&at=<company>` with `?career=`.

On Your jobs each company has Careers (`components/versions/CompanyCareers.tsx`): adding one is choosing a career; editing one (`/employer?company=<id>&career=<id>`, `components/versions/VersionEditor.tsx`, draft logic in `lib/versionDraft.ts`) is the path itself: a tap leaves a skill out or puts it back, a search adds one, a skill's makes are chips under it, and each tap is saved as it is made (one save at a time, whole lists). Deleting asks first.

## Military careers

A military job (a Navy rating, an Army MOS, an Air Force specialty) is a career with a service, and each service is an employer: a company whose `service` is `navy`, `army`, `air-force` or `marine-corps` (migration 0061), with no factories. A military career carries `service_company_id`, `code`, `code_system` (`navy-rating`, `army-mos`, `afsc`) and `official_title`; its title keeps the service in front ("Navy Electronics Technician"), because a title is unique. The words above the name and the tags are derived in `shared/military.ts`, never stored. They are curated in `data/careers/military/` (`employers.json`, `careers.json`, `paths.json`), apart from the civilian catalogue, so the posting reader, `industry_occupations` and every count of 156 never see them. `scripts/build-military-sql.mjs` checks them (`--check`; `--report` prints the civilian careers each reaches) and generates 0062 to 0064, which decide in SQL and write to `load_log` (loads `military-employers`, `military-careers`, `military-paths`). A service is found by its key, else its exact name; a career by its code, else its exact title, and a civilian career is never taken over. Every path loads as a draft, and one a person approved is never replaced. There are 118: 39 Navy, 44 Army, 35 Air Force; the Marine Corps has none yet. Codes and titles were checked against the Defense Manpower Data Center's file of July 2024 (two delivered codes were obsolete and are in the file's `dropped` list); one path, Navy Hull Maintenance Technician, was read against its official task list, and each path's `basis` says which.

A military career is on no ladder and typical of no industry. What joins it to civilian careers is arithmetic, never a table of codes: the share of a civilian career's path its own path's skills cover. **Military careers are reached on purpose: every default list, count, search and suggestion is of civilian careers** (`civilianCareer()` and `civilianPathLine()` in `server/lib/military.ts`): `GET /api/occupations` (so the career picker and the job form), `/api/search`, `/api/stats/counts`, Explore's overview and facets, careers within reach, suggested skills, and every count of the careers that use a skill. A goal, a job or a company's version for a military career is refused (400). A skill only military careers use (`militaryOnlySkill` in `server/lib/military.ts`) is in the taxonomy and the Atlas, whose panel says how many military careers use it (`militaryCareers` on each skill of the taxonomy), and is left out of the Skills list in every order and of the counts; the Skills list narrowed to its own group lists it (`GET /api/skills?group=` is that group's skills, whichever careers use them).

Where one is asked for:
- **The Careers list** has a Civilian | Military filter beside the others (`?military=1`, `?service=navy`; `components/explorer/FilterBar.tsx`). With it on the list is the military careers alone, each row with its kind and code in the grey line ("Navy rating · HT"), the count says what is listed ("39 Navy careers"), Domain offers only the homes those careers have (`militaryCareerDomains`), and the list also finds a career by its code. Explore's counts stay civilian.
- **The header's search** lists a military career only when the query names it (`readMilitaryQuery`, `namesCareer` in `shared/military.ts`, applied by `namedMilitaryCareers` in `server/lib/military.ts`; `/api/search?military=named`, which only the header sends): its code alone ("15T"); its service with its code, with whole words of its title or with their first three letters or more ("navy hull"); or its code with its system's word ("HT rating"). A code that is ordinary letters (`PLAIN_CODES`: a word, a state, a unit, another name of a skill, a common abbreviation; 21 of the Navy's 39) counts only beside its service. A named career is first among the careers, and leads the results only when the query can be nothing else (`namesForSure`, `leads`): a code with a digit, or a code beside its service or its system's word. A service's name and nothing else lists the service among the companies (`namedService`). A plain "welder" lists civilian careers only. The map's search never asks, and neither a military career nor a service is ever the map's subject.
- **Profile**: "Start with what you have done" (see "Seekers: skills and reach").

Reach between a military career and a civilian one is arithmetic over the two paths, never a table of codes: the civilian career is within reach when the military career's skills cover a third or more of its path, and that path has five skills or more (`withinReach` in `shared/reach.ts`, the same rule as Profile's; `server/lib/reach.ts` reads it). `GET /api/occupations/:id` carries `reachedBy` for a civilian career, drawn as the page's last section, "Military careers that reach this" (each row its kind and code and "12 of 19 skills"; no section when none does), and `withinReach` for a military one. A skill's page ends in "Military careers that use it" (`militaryOccupations`). On screen the words are "military careers that reach this" and "civilian careers within reach"; "military" is a word of the filter and of those sections, never a badge.

A military career's page is the career page (`components/entity/OccupationDetailView.tsx`): its kind and code above the name ("Navy rating · HT"), the service's own title as the name (lists and search keep the full title; one longer than any of the catalogue's takes `longTitle`), and its service as the first fact, a link to the service's page, before its home. It is where a person comes from, never a goal: a seeker's one action is "I have done this" (`components/account/DoneButton.tsx`: the door's own write in place, with Undo and then "Open Profile"); a visitor is shown the way to sign in and someone here to hire no action. Its path draws like any career's, with "Draft" beside the heading. After the path comes "Civilian careers within reach" (`withinReach`): five rows and "Show all", each the career, "12 of 19 skills", and under it the skills missing, lowest level first, with "Compare on the atlas" (`/atlas?career=&with=`). It has no ladder, industries, jobs, companies or factories, and draws none.

A service's company page is headed "Military service", has no factories and no map action, and lists its careers (`serviceCareers`). A service is not an employer to join: the company finder on Your jobs does not offer it, and a membership, a request for it or for a factory of it, a factory, and a version of a career for one each answer 400 (`isService`, `notAnEmployerHere` in `server/lib/military.ts`). A career's `leadsTo` takes no military career at either end; a career that has goals, jobs, industries, factories, ladder links or versions is not given a service; and a military career and a civilian one are not merged into one another (409).

## Careers and factories

Two different links, kept apart:
- `factory_occupations`: careers recorded for one factory (headcount, pay). Empty in production today.
- `industry_occupations`: careers typical of an industry (the 21 NAICS manufacturing subsectors in `factories.primary_naics_description`), curated in `data/careers/industries.json` (see "Careers"; every career of the catalogue is listed for some industry). It says what kind of work an industry has, never that a given factory employs it, and the wording on screen keeps that distinction ("Careers in this industry", "Where this work is done").

From it: a career lists its industries with factory counts and leading states (`GET /api/occupations/:id` → `industries`, `everywhere`, `elsewhereToo`, `topStates`); a factory with no recorded careers lists its industry's (`GET /api/factories/:id` → `typicalCareers`), and so does a company whose one factory has none (`GET /api/companies/:id` → `typicalCareers`); a state or focus area lists the careers its industry mix points to (`careers` on the map overviews, weighted toward each industry's leading careers). Careers marked `common` (found in every industry) are left out of area lists.

## Industries

An industry is one of the 21 NAICS manufacturing subsectors (`INDUSTRIES` in `shared/industry.ts`: code, slug, and the name a factory carries in `factories.primary_naics_description`). `/industries/:slug` is its page for the country, a state (`?state=TX`) or a focus area (`?area=austin`); `/industries` lists all 21, largest first, as a tab of Explore (`components/explorer/IndustryList.tsx`). Two kinds of figure are kept apart: official statistics (`industry_stats`: people employed, establishments, average pay, by state and for the nation, from the Bureau of Labor Statistics' QCEW; none for a focus area) and what the product lists (factories, companies, and people at a factory whose `workforce_size` is recorded). An unknown headcount is null, never zero: an employer's people are summed over the factories that have one, and the page says "People at 2 of 5 factories" when that is not all of them. The page's Companies are ordered by people where a headcount is recorded, otherwise by factories. Link to an industry with `industryPath(name, { state | area })` (`shared/industry.ts`), which returns null for a name that is not one of the 21. The statistics come in through `scripts/ingest/qcew.mjs` (writes `data/industries/qcew-<year>.json`) and `scripts/build-industry-stats-sql.mjs` (generates the migration): another year is a new JSON file and a new generated migration.

A company's industry is the one most of its factories are in (`leadingIndustry` in `shared/industry.ts`; `companyIndustry` and `companyIndustries` in `server/lib/industries.ts` for SQL); a tie goes to the name that sorts first. It is shown through `shownIndustry`, which gives the short name for one of the 21 and null for anything else; a company's page shows up to two, read from its factories. `companies.industry` is free text that the record API still stores: it is not shown or searched, no list filters by it, and the admin form does not offer it.

## Skills

The skills catalogue is curated in `data/skills/catalogue.json` and loaded by `scripts/build-skills-sql.mjs`, whose migration restates the whole catalogue (`0033_skills_catalogue.sql` first, then `0048_skills_catalogue_2.sql`, `0057_skills_catalogue_3.sql`, `0059_skills_catalogue_4.sql` now: 722 skills; a unit check fails when the file and the latest disagree). It stops, changing nothing, when a stored skill is one the file does not know; it adds a kept skill that is not stored; it attaches nothing to a career. It says in `load_log` (load `skills-catalogue`) each name it added and, with `look = true`, anything a restated catalogue put back: a description or tools line corrected by hand, a skill renamed, merged or removed, a name stored for another skill. A pass that adds, merges, renames and removes no skill (0057: 25 other names employers' postings use) needs no taxonomy migration after it. A skill is something specific a person can learn, be shown doing and be hired for; a material, a specification, a product name, a duty or a trait is not one. A skill is the standard one: a brand is never a skill but a make of one. Every skill has a `description` (what it is, then "A person who has it …"), `how_learned` (on the job, a course, an apprenticeship, a credential: named only when it is real and current) and `tools` (a short list). A merged or renamed skill keeps its old name in `skill_aliases`. A skill's tools line names kinds of thing and no make (a unit check holds it).

**Makes.** A skill that depends on equipment or software has makes: the named machines and software it is run on (CNC Control Operation: Fanuc, Haas, Siemens; PLC Programming: Studio 5000, TIA Portal). A make is a leaf beyond the skill and never replaces it. They are curated in `data/skills/makes.json` (what makes exist for a skill, never what a company runs) and loaded by `scripts/build-makes-sql.mjs` (migration `0050_skill_makes.sql` first, `0058_skill_makes_2.sql` now; `--check` validates and writes nothing; a unit check fails when the file and the latest disagree; `load_log`, load `skill-makes`, has each make added and, with `look = true`, any spelling or order the file put back) into `skill_makes`. A make stored under the same name keeps its id, so people's marks stay; a make the file does not list stays, after the file's. A person marks the makes they have run in `user_skill_makes`, which the database ties to their holding of the skill and to a make of that skill: taking the skill off the list takes its makes with it. `GET /api/skills/:id` carries `makes: [{ id, name }]`, each skill of `GET /api/skills/taxonomy` its makes' names, `GET /api/me/skills` the ones the person marked; `PUT /api/me/skills/:skillId/makes { makes: [id] }` sets them as a whole list (409 for a skill off the list, 400 for another skill's make). The skill page has one section, Makes, after Group: quiet chips, toggles for a seeker who holds or is learning the skill; Profile says a person's makes as the second line of the skill's tag; a career's path shows none. Skill search also matches a make. `server/lib/makes.ts` holds the reads and a person's marks.

**The taxonomy** is three deep: every skill is in one **skill group** and every group in one **domain** (a department a large manufacturer has). Every skill also has one **level**, the same in every career: 1 Fundamentals, 2 Intermediate, 3 Advanced (`shared/skillLevels.ts` holds the names and the few words under each; the client reads them through `lib/stages.ts`). The taxonomy is curated in `data/skills/taxonomy.json` (domains, groups and skills in the order they are shown; a group holds 2 to 12 skills; every skill of the catalogue is placed exactly once) and loaded by `scripts/build-taxonomy-sql.mjs` (migration `0060_skill_taxonomy_3.sql` now, 0042 and 0049 before it: 143 groups; `--check` validates the file and writes nothing; a unit check fails when the file and the migration disagree). It lives in `skill_domains`, `skill_groups` and, on `skills`, `group_slug`, `level` and `group_position` (the skill's place in its group as the file orders it; a skill placed by hand has none and sorts after the rest of its level). `skills.category` is kept and holds the domain's name; the API neither returns it nor filters by it. The catalogue's `category` is still checked by the catalogue's builder and is shown nowhere.

A career's path is its skills laid out by their own levels: a path sets no stage. `occupation_skills.stage` is kept and always equals the skill's level, held so by two triggers that 0042 creates: `occupation_skills_stage_is_level` (a row written to a path takes its skill's level whatever it was given) and `skills_level_moves_paths` (a skill whose level changes moves in every path). A career has a path when `occupations.path_status` is set (`draft` or `approved`). Any career with skills has a path to draw; `path_status` decides only the word "Draft" beside the heading.

A career's path is drawn as a flow (`PathFlow` in `components/path/`, from `buildPath(skills)` in `model.ts`): one trunk through the three levels, a branch for each domain a level draws on, each skill group one header line (`SkillGroupBox`: the name and, for a seeker, how much is held) with its skills as tags under it. It runs down a phone and across a wide screen from the same markup (a container query on `.path-flow` in `globals.css`); the lines are drawn by the layout, never measured. All three levels are always drawn; an empty one says so. `comesFrom` and `leadsTo` on `GET /api/occupations/:id`, when present, are drawn before the first level and after the last. The parts take a path as data, so the same ones draw a skill's group on its page and a person's skills on Profile, and will draw a company's version of a career; a tag can carry a second line (`note`) for a make.

A skill carries its `level`, `group` and `domain` (the last two as `{ slug, name }`; `server/lib/taxonomy.ts` reads them) on the skills list, on its own page and in a career's `skills`. All three are null only for a skill no migration placed, as in a local database filled by `npm run db:seed` alone. `GET /api/skills/taxonomy` is the whole tree in one answer: the levels, then every domain with its groups and their skills, each skill with its `level` and how many careers use it (`careers`). The client reads it with `useTaxonomy()` in `lib/queries.ts`, kept for the visit and refreshed when an admin changes a skill, a career or a path (`recordsChanged` in `lib/records.ts`).

The skill page is one request (`GET /api/skills/:id`): the details, its level, group and domain, the other skills of its group (`groupSkills`), the careers that use it, the industries those careers are typical of, the skills whose careers overlap most with its own (`relatedSkills`, each with its level and group) and open jobs that ask for it. Under its name the page links its domain and its group, each into the Skills list narrowed to it, and says its level. Its first section is its group (`#group`): the group's line with all its skills as tags under their levels, this skill the one that is not a link. `GET /api/skills` lists only skills a career uses, the ones most careers use first (`sort=name` for name order), narrowed by `domain=` and `group=` (slugs) and `level=` (400 unless 1, 2 or 3); with `search` it matches the name, another name (`skill_aliases`) and a tool, and also finds a skill no career uses yet. `/api/search` matches those and the name of a skill's group or domain, and says "Also called …" when it found a skill by another name.

## Atlas

`/atlas` is the Atlas of Manufacturing: every skill in one radial tree (centre, domain, skill group, skill), drawn in SVG from our own arithmetic (`components/atlas/layout.ts`; no charting library). Angles come from leaf counts, with a gap between groups and a wider one between domains, in the taxonomy's order. A skill's level sets its band (Fundamentals nearest the centre, Advanced at the rim), and within a band the leaves take three rows in turn so each keeps its own mark. A skill more careers use is a larger, brighter mark. It is drawn by Explore under the Skills tab; the Skills list and the Atlas are two views of one thing with one switch between them (`SkillsViewSwitch`), never a seventh tab.

The address is the state: `?domain=`, `?group=`, `?skill=` (one is written, the most specific), `?career=<id>` lays a career over it and `&with=<id>` a second. Build links with `atlasHref` (`components/atlas/state.ts`). Opening a domain turns it to three o'clock and enlarges the plate (one CSS transform on one group); its groups are named beside it, an open group's skills in the group's place. The panel beside the drawing (under it on a phone) is the same tree as links, one branch at a time, and is what the keyboard and a screen reader use; the SVG is one image. Its skills are the same tags a career's path uses (`.skill-tag`), here links that open the skill on the atlas.

The plate itself (`Plate`) renders once per taxonomy. A career, a person's marks, labels and what the pointer is on are small layers over it, and the pointer is read by arithmetic (`locate`, `unproject`): never put a listener on a leaf or re-render the plate for a hover. The accent is used only for an overlaid career and the selection: the first career's skills are a disc, the second's a ring, shared ones the disc in the ring. A seeker's own skills carry the product's mark (held filled, learning half); nobody else has marks. The drawing waits for one request, the taxonomy, which `App.tsx` asks for before the page's code has arrived; a career is one more (`GET /api/occupations/:id`). Everything the Atlas draws is styled by the `.atlas-*` rules in `globals.css` (theme tokens only; lines keep their width with `vector-effect: non-scaling-stroke`).

A career's page shows its path two ways, with one switch in the Path heading (`PathViewSwitch`, the same control as List | Atlas: `components/layout/ViewSwitch.tsx`): the flow, and the Atlas (`?path=atlas`; `&domain=<slug>` for a domain opened on the plate). The view the address names is kept for the visit (`archangel.pathView`, session storage); with nothing named or kept it is the flow. The Atlas view (`components/atlas/CareerAtlas.tsx`, loaded with the Atlas's code only when asked for) is the plate with the career laid over it and, under it, the career's skills as tags by level and group. On a phone the plate holds still under the header while the tags move under it (never taller than about half the screen; under 560 px of height it scrolls with the page); from 1024 px the two stand side by side. Pressing a domain the career reaches, or its word under the plate, turns to it and narrows the tags to the career's part of it; "Whole path" goes back. It ends in "Open in the atlas" (`/atlas?career=<id>`).

While a seeker fills in the one career laid over the atlas (on its page, and on `/atlas?career=`, where the panel's tags for the career's skills carry the mark and the career's line reads "N of M skills held"), the drawing is the path, part walked (`walk` on `AtlasDrawing`): a skill still ahead is an open mark in the accent; a held one is bright, with the way to it from the centre drawn bright over the career's branch (`routePath` in `walk.ts`); one being learned is the half mark; and the root at the centre is the ring of how much is held, which closes into the ticked disc when the career is whole. Bright is the person, the accent is the career: no other colour, and no message for a level or a career completed. Two careers are compared, never walked. A visitor and someone here to hire see the career's shape with no marks.

What moves is never in the plate's SVG. The ring at the centre and the answer to a mark (the way drawn in from the centre, the mark arriving, one ring opening from the leaf: about a second, off under `prefers-reduced-motion`) are a second small SVG laid exactly over the plate under the same camera (`.atlas-moving`, its own compositor layer): a frame of motion inside the plate would repaint all of it. The lasting line and mark are added to the plate's layers at once but unseen (`data-arriving`) until the answer is done (`useFreshMark`). A mark adds or removes one path and one mark; nothing in `Plate` changes.

Profile shows each goal's career as a small plate (`GoalPlate`: no names, no camera, none of the leaves): one shared ground on the page (`GoalPlateGround`, an SVG symbol) and at most five paths per goal, drawn from `skillIds` on `GET /api/me/goals` and the person's skills. It opens the career's Atlas view (`careerAtlasHref`). Careers within reach stay words.

## Detail pages

Company, factory, career, skill, industry and job are one template, written out at the top of `client/src/components/layout/Page.tsx` and built from `DetailHeader`, `DetailFacts`, `DetailSection`, `RecordList` / `RecordRow` and `ShowAll`:
- The heading block: the way back alone on the first line (an admin's Edit at its end), the kind in small capitals above the name (a job reads "Job #N" only to people who manage it), the name with the company's mark before it on company, factory and job, one paragraph, one or two quiet lines of facts, then the page's one action: Open on the map (company, factory, industry), Set as goal (career), Not held / Learning / Held (skill). A job's action is a form, so it is the Apply section after the job's terms.
- Sections, in this order, leaving out what the page does not have: what it is, where, open jobs, companies, factories, careers, skills.
- A list of records is rows with a hairline between them and no box: the name, at most one grey line, a chevron or the row's figure. `RecordRow` takes `below`: a line under the link that is not cut short and may hold a link of its own (the skills a career within reach still asks for). No icon per row; a company's mark may lead its row and a skill's row may carry its mark. Three other shapes exist, each for one thing: figures by place (`FigureList` in `components/industry/parts.tsx`), chips for states that open on the map, and skills on a path, which are tags under their group's header line (`components/path/`).
- A company with one factory leads with that factory's facts and address in place of a list of one.

## Words

On screen an occupation is a **Career**, and a job is one opening for a career at one factory. The place where things are made is a **Factory** on every screen and in every message and email (**Factories**; "factory" in running text), never a plant: `tests/unit/words.unit.ts` fails when one says otherwise. The word plant stays only in the name of a real site ("Kentucky Truck Plant"), in another sense (a power plant, "Plant utilities", "Nuclear plant operations"), in code where it is already written (`plant_merge`, `PlantPicker`, `?plant=`, the `plants` field), and in scripts and the notes kept with the data (a `load_log` line, a research file). What a script or the database words for a screen says factory too: a match's reason (`scripts/ingest/lib/pipeline.mjs`), and a refusal of `plant_merge`, reworded before it is shown (`SAID` in `server/lib/plantPairs.ts`). Headcount is **people**, never workforce or employees. A career someone aims for is a **goal** ("Set as goal", "Goal", "Goals"). `/me` is **Profile** and `/employer` is **Your jobs**. A plain account has no role label. An **Industry** is shown by its short name (`industryLabel`); **Establishments** is the official count of workplaces and **Factories** are the ones the product lists. A place is written "City, ST". On a job's page and the account pages a day is "today", "yesterday", then "Nov 18", with the year only when it is not this one (`formatDay` in `lib/dates.ts`); only History gives the time. An empty list reads "None yet." Code, routes and tables say `occupation` and `factory`. A skill's level is **Fundamentals**, **Intermediate** or **Advanced**, the same in every career. A domain is shown by its name alone ("Quality", never "Domain: Quality"); a skill group by its name, and called a group where a noun is needed ("All groups").

## Users

Roles are relationships, not account types (`server/lib/auth.ts`):
- **Seeker**: any signed-in person. Owns their skills (learning/held), career goals and applications.
- **Employer**: a person with an active membership in a company (`company_members`). A join request is approved by an admin.
- **Admin**: `users.is_admin`, and nothing else: there is no admin key, header or setting that opens a write. The first admin signs up in the app and is then made one on the command line (`node scripts/make-admin.mjs <email>`, which reads `DATABASE_URL`). After that, admins make admins from Admin Tools. Nobody removes their own admin role, and the last admin cannot be removed. Every route that changes a company, factory, career or skill, and all of `/api/admin/*`, takes a signed-in admin: 401 signed out, 403 otherwise.

**Purpose** (`users.purpose`, migration `0034`; rules in `shared/purpose.ts`): what an account is for, `work` or `hire`. It decides which tools are drawn and never what is allowed. Set at sign-up (`POST /api/auth/sign-up { purpose }`) or in settings (`PATCH /api/me { purpose }`). While it is unset it is read from the person's ties to a company: a membership, a request to join one or a request to have one added means `hire`. `GET /api/auth/me` returns it as `user.purpose`.

**Tools by person** (`useViewer()` in `client/src/lib/viewer.ts`): a seeker is shown their profile, goals, skill marks and Apply; an employer their jobs and applicants, and no goals, skill marks or Apply; an admin Admin Tools and Edit, plus the tools of their own purpose. One set at a time. A seeker's control asks `useSeekerTools()`, a "Post a job" prompt `usePostJobLink()`. Pages reached by their address always work.

**View as**: an admin chooses in settings to see the app as a user or an employer. It is kept in the browser (`archangel.viewAs`, `<user id>:<view>`), changes only what is drawn and sends no request differently. While it is on, the header's wordmark is replaced by one sign (`components/account/ViewAsSign.tsx`; on a phone the eye alone) that returns to the admin view in one press.

**Invites** (`invites` table, `server/lib/invites.ts`): an admin creates a one-time link for an email address (`/sign-in?invite=<token>`), as a user, an employer of one company, or an admin. The link is shown once (only the token's hash is stored), lasts 14 days, and there is one pending invite per address. When mail is on the link is also emailed to the address; when it is off the admin passes it on. Signing up through it creates the account, applies the role and marks the invite accepted in one transaction. An address that already has an account is not invited; its roles are changed under People.

**Passwords** (`password_resets` table, `server/lib/passwordResets.ts`): a signed-in person changes their own in settings (`POST /api/auth/password { current, next }`), which ends their other sessions. Someone who cannot sign in gets a one-time link from an admin (People → Manage → Password reset link; `POST /api/admin/users/:id/reset-link`). It opens `/sign-in?reset=<token>`, is shown once (only the token's hash is stored), lasts 24 hours and replaces any unused link for that person. Using it sets the password, ends all of that person's sessions and signs them in. When mail is on the link is also emailed to the person, and "Forgot password?" on the sign-in page sends one without an admin (`POST /api/auth/forgot { email }`: the same answer whether or not the address has an account, given before any account is looked up). When mail is off the admin passes the link on and the sign-in page says so.

**Admin Tools** (`/admin`, `client/src/pages/Admin.tsx`, tabs in `client/src/components/admin/`) is reached from "Admin Tools" in the account menu, shown to admins only. Tabs (`?tab=people|access|invites|data|history`):
- `people`: search by name, email or company (`?q=`), by role (`?role=admin|employer|waiting|user`), the open person (`?open=`); roles, company access, name and email corrections, "Sign out everywhere", delete.
- `access`: requests to join a company (approve and decline carry Undo), and requests to add a company or factory.
- `invites`: pending, and earlier (accepted, expired). Admin invites last 3 days, others 14.
- `data`: find a record to correct or add one, and career paths (drafts and approved). With `&kind=company|factory|career|skill&id=<uuid>` the tab is that record's editor (`components/admin/RecordEditor.tsx`): its fields, a career's path (`#path`), Merge, History, Delete. An admin sees **Edit** on a record's own page; it opens the same editor. One form adds and corrects (`components/admin/RecordForm.tsx`); for a career it sets Home (a domain, or none) and Leads to (`components/admin/LeadsToField.tsx`: up to three, found by search, order kept), and a career keeps up to 80 other names; for a skill it chooses a Group (every group, listed under its domain) and a Level, and adding one needs both. A skill's editor also lists its makes (`components/admin/MakesEditor.tsx`): add, rename, move, remove, each saved as it is made and audited in words (`addSkillMake`, `renameSkillMake`, `removeSkillMake`, `orderSkillMakes` in `server/lib/records.ts`; `POST`, `PUT { order }`, `PATCH /:makeId`, `DELETE /:makeId` under `/api/skills/:id/makes`); removing a make people have marked says how many and asks. A merge of skills moves makes and marks. A career's path (`components/admin/PathEditor.tsx`) adds and removes skills and shows each under its own level: a level is changed on the skill's record, never on a path. The tab also leads to "Factories listed twice" while pairs wait (`?tab=data&pairs=id`: two rows carrying one registry id, with the cleanup's reason; Merge with the row to keep chosen there, or Two factories, which has Undo; `components/admin/PlantPairs.tsx`). Under them, Data quality (`components/admin/QualityTable.tsx`, `GET /api/admin/quality`, `server/lib/quality.ts`): one table by state of how many factories have an industry, a clean code, a county, a headcount, an address and an outside id, companies with one factory, and factories that share company and spot (coordinates equal to three decimals); the definitions under the table and in `quality.ts` are the same words. Its Duplicates count opens the factories of one company on one spot (`pairs=spot&state=TX`) and does not count a pair said to be two factories. The tab opens with the matches a source's run was not sure of (`components/admin/MatchReview.tsx`: Same, Different, Skip, each audited as a `factory` line; drawn only when some wait, and counted in the Waiting line) and lists the sources with their latest runs (`IntakeSources.tsx`).
- `history`: what admins changed (`?show=<kind>`).

To anyone who is not an admin the page is the not-found page. An action says what it did through `useAdminNotice().say(message, { undo, focus })` (`components/admin/AdminNotice.tsx`); `focus` is where the keyboard goes when the action removed the row that had it.

**Records**: a company, factory, career or skill is changed through `server/lib/records.ts`, whichever route it arrives by (the kind's `PUT` / `DELETE`, or `PATCH /api/admin/companies/:id`). Each field is checked, a refusal carries `field`, and the audit line is written in the same transaction. A factory an admin gives people, products or an opening year counts as curated, and an admin's edit to a factory marks the facts it set as the admin's (`adminSetFacts` in `server/lib/provenance.ts`), so no source's run replaces them. A skill's group and level can be changed and never cleared; the audit line names the group, the domain and the level in words. A merge (`POST /api/admin/records/:kind/:id/merge { into }`; company, career, skill through `server/lib/recordMerge.ts`, and factory through `plant_merge`: `server/lib/plantPairs.ts`; a factory keeps no other name, its merge answers `took`, and a curated factory into an uncurated one is refused with 409) moves everything to the kept record (a career's links too, dropping any that would point it at itself or close a ladder), writes `record_merges` and keeps the merged name as an alias (`companies.aliases`, `occupation_aliases`, `skill_aliases`). Adding or renaming warns of near-duplicates (`GET /api/admin/records/:kind/similar?name=`; `server/lib/recordSearch.ts`).

**Audit**: `audit_log` (migration `0025_admin_upkeep.sql`, `server/lib/audit.ts`). Every admin write calls `recordAudit` with who, kind (`company | factory | career | skill | person | access | invite`), the record, the action and a short before and after; read with `GET /api/admin/audit?kind=&record=&limit=&offset=`. A new admin write must add its line. A factory's merge and the pairs kept apart are `factory` lines (`merged`, `kept apart`, `no longer kept apart`). An admin's write to a company's version of a career is a `company` line (`career version added | changed | deleted`); a member's is not audited: the version row says who last changed it.

**The first admin** is the one with the earliest `users.admin_since`; another admin cannot remove that role or delete the account (handing it on takes SQL). The most common passwords are refused.

**Records by hand** (`components/admin/Records.tsx`, `lib/records.ts`): the Data tab's find-or-add. One company, factory, career or skill is added through the validated POST endpoints. An add names what was added with a link to its page; a duplicate (409) links to the record that is already there. There is no spreadsheet import: data in bulk comes from scripts and generated migrations (see `README.md`).

Sessions are an HttpOnly cookie; only the token's hash is stored. Signed-in responses are `no-store`.

## Email and notices

**Sending** (`server/lib/email.ts`): `sendEmail` / `sendEmails` call Resend's HTTP API with `fetch` (no SDK). Mail is on only when `RESEND_API_KEY` and `EMAIL_FROM` are both set; off, every caller carries on as before and the interface keeps its "passed on by hand" wording. Every link in an email is built from `APP_URL` (default `https://www.o-10.com`), never from a request. Outside production `EMAIL_OUTBOX=<file>` captures emails as JSON lines instead of sending them and counts as on. `GET /api/auth/options` → `{ email }` tells the client (`useEmailOn`). Sending never throws into a caller, waits at most four seconds, and logs only the kind of email and the cause.

**What is sent** (`server/lib/notices.ts`, wording in `server/lib/emailTemplates.ts`: text first, an HTML twin in one plain column):
- Sign-in emails, always when mail is on: an invite; a password reset (asked for on the sign-in page, or made by an admin).
- Notices, unless the person turned them off (`users.email_notices`, the switch in settings, which a notice's last line links to): a company access request (to the admins), its approval or decline (to the requester), a new application (to the company's active members, at most one per job per member per hour; the next says how many more applied), an application's stage changed by the company (to the applicant). A withdrawal emails nobody.
- A notice is sent after the write it reports, and a failure to send never fails the action. Limits are kept in `notice_log`.

**Without email:**
- A declined access request is kept: `company_members.status = 'declined'` with `decided_at` / `decided_by`. The employer page says so, the same company cannot be asked again for 7 days (409), and Admin Tools lists the last 30 days of declines with "Approve after all". `decision: 'remove'` on `PATCH /api/admin/memberships` deletes the row, whatever its state.
- An application's history is in `application_events` (written on apply, on every stage change, on withdrawal). `/api/me/applications` returns each application's `events` and `changed`; `/me` shows the stages with dates and, at Interview and Offer, that the company will contact the person at their account email.
- The account button shows one dot in full ink, never a count, when `GET /api/me/news` → `{ applications, applicants, access }` has something true. It is cleared by opening the page that shows it (`POST /api/me/seen`; `users.applications_seen_at`, `applicants_seen_at`, `access_seen_at`): `/me`, the employer page or a job the person manages, the Access tab. In the menu the page with the news stays bright and the rest step back.
- Admin Tools opens with a "Waiting" line (access requests, requests to add a company or factory) only when someone waits. Draft career paths are work, not someone waiting: they are listed under Data. An access request shows the person's address beside the company's domain and how many people already have access.

Migration `0024_email_notices.sql` adds all of the above. `tests/api/email.sh` checks it against a server started with `EMAIL_OUTBOX` (give the script the same file as `OUTBOX`, and the same `APP_URL`).

## Routes

**Public:** `/map` (opens on the US; `?area=austin`, `?state=TX`), `/explore`, `/jobs`, `/jobs/:id`, `/companies/:id` (id or slug: `/companies/tesla`), `/factories/:id`, `/occupations/:id` (career page with path, a military career's included; `?path=flow|atlas` and, on the atlas view, `&domain=`; `?at=<company id or slug>` is that company's version of it), `/skills/:id`, `/industries`, `/industries/:slug` (`?state=`, `?area=`), `/atlas` (`?domain=`, `?group=`, `?skill=`, `?career=`, `&with=`, `&at=`), `/sign-in`, and `/settings`, which signed out shows Appearance and the way to sign in (the sign-in page links to it)

`/explore` is one page with six views under one heading and one tab row (`components/explorer/ExploreNav.tsx`): Overview, Industries (`/industries`, drawn by Explore), and the lists at `?tab=companies|factories|occupations|skills`, on screen Companies, Factories, Careers, Skills. The lists are filtered and sorted from the address (`state`, `industry`, `domain`, `group`, `sort`); factories open on Most people (known headcounts first, largest first, the rest by name), careers on Most skills. The Skills list opens in the taxonomy's order ("By domain": domain headings, groups, each skill with its level, `components/explorer/SkillTree.tsx`, read from the taxonomy answer); `sort=careers-desc` and the name sorts are the plain list. Skills are narrowed by domain, then by one of its groups; careers by `domain` (their home), and by `military=1` or `service=<key>` (see "Military careers"). The overview (`components/explorer/ExploreOverview.tsx`) has one section per tab, in the tabs' order, under four figures; a list's own count sits between its filters and its rows.

**Signed in:** `/me` (Profile: applications, goals, skills), `/settings` (name and ZIP code, email, password, email notices, theme, what the account is for, View as for admins, delete account), `/employer` (Your jobs, for company members; `?company=&career=` is the editor of a company's version of a career), `/admin` (Admin Tools, admins)

Old addresses: `/import` and `/import/bulk` redirect to `/admin?tab=data`; `/tree` redirects to the map. Anything else unknown (including the removed `/refs/:id`, `/schools/:id`, `/programs/:id`) is the not-found page.

**Header** (`components/layout/Layout.tsx`): Map, Explore and Jobs are words at every width, with no icons. The wordmark links to the map and is dropped on a phone. Explore is lit for `/industries`, `/atlas` and every company, factory, career and skill page. For someone here to hire the third item is "Your jobs" (`/employer`); the account menu lists Your jobs only while applicants are waiting, and a profile for someone here to hire only while an application has news, so the dot always leads somewhere.

**Search**: the header's search (`components/search/GlobalSearch.tsx`) and the map's share `components/search/results.ts`: the groups, their words, one order (States and areas, Industries, Companies, Factories, Careers, Skills, Jobs, then the map's Places) and the scoring. A group holding exactly what was typed leads. Rows carry no icon: a company its logo. With nothing typed the header's search is the field alone, with recent searches if there are any.

## API Endpoints

- Public reads: `/api/companies` (`?industry=` takes one of the 21 by name or slug), `/api/factories` (`sort=workforceSize`; `/pins` is the map's packed pins, `shared/pins.ts`, and takes `states` and `company`), `/api/occupations` (careers with a path first, then the most skills; `sort=name` for name order; a row's `levelCounts` is how many of its skills are at each level; rows carry `home: { slug, name } | null` and take `domain=<slug>`, an unknown slug giving an empty list; `/:id` carries `home`, `leadsTo` in the catalogue's order and `comesFrom`, always present), `/api/skills` and `/api/skills/taxonomy` (see "Skills"), `/api/search` (companies, factories, careers, skills, industries, open jobs as `results.jobs`, and states from `shared/states.ts`; a factory's `subtitle` is "Company · City, ST", a company's its industry's short name or nothing, a skill's its group unless it says "Also called …"), `/api/map/*` (with `factories/:id/county` → `{ county, metro, manufacturing }`, `county` null for a factory not yet placed), `/api/stats/counts` (companies, factories, occupations, skills, total), `/api/explore/overview` (everything the Explore overview shows, in one response), `/api/explore/facets` (what the browse lists filter by: `industries: { plants, companies }` and `skillDomains`, the domains with a skill some career uses, each `{ slug, name, groups }`, in the taxonomy's order, and `careerDomains`, the domains that are some career's home), `/api/jobs`, `/api/jobs/:id`, `/api/industries?state=|area=` (every industry in a place, with manufacturing as a whole) and `/api/industries/:slug?state=|area=` (the industry page in one response). `/api/jobs` GET answers `{ jobs, total, limit, offset }` and takes `q`, `occupationId`, `companyId`, `factoryId`, `skillId`, `state`, `near`, `within` (with `near` each job carries `miles`, nearest first; otherwise `jobsInOrder()`), and `/api/jobs/summary` is how many jobs are open and the states that have some; a job from a careers site carries `fromSource`, `levelWord`, `levelRank`, `requirements`, `lastSeenAt`, `undated`, and each of its skills its `makes`; a company's, factory's, career's and skill's record carries `openJobCount` beside its twelve newest open jobs; the map overviews (`states/:code/overview`, `areas/:id/overview`, `bounds/overview`) carry `openJobs` and `jobs`, listed in the panel only when there are some. `/pins` and `/api/map/state-counts` answer 400 to a query parameter they do not take, `?industry=` on the pins included (`onlyQuery` in `server/middleware/cache.ts`). Wherever a route takes `limit` it is read as a whole number from 1 to the route's most (`1.5` is 1)
- Depth: `/api/factories` rows and `/api/factories/:id` carry `workforceSize`, `workforceYear`, `workforceSource`, `workforceNote`, `products`, `openedYear`, `status`, `curated`; `:id` also `sources`. `/api/companies/:id` carries `parent`, `subsidiaries`, `headquarters`, `peopleByState`, `sources`, and each factory's depth and address
- `/api/auth/*` sign-up (takes an optional `invite` token), sign-in, sign-out, me, `options`, `invite/:token` (what an invite grants; 404 when unknown, used or expired, with `reason: used | expired | unknown`), `password` (change your own), `forgot`, `reset/:token` (whose password a reset link sets; 404 when unknown, used or expired), `reset` POST `{ token, password }`; `email` POST `{ email, password }` changes the sign-in address (ends other sessions, tells the old address by mail)
- `/api/me/*` profile, `news`, `seen`, skills, `skills/suggested`, goals (each with `next` skills and `skillIds`, every skill of the career by id), applications, `careers/reach`; `DELETE /api/me { password }` deletes your own account with its skills, goals, applications and memberships (posted jobs stay; not the last admin)
- `/api/jobs` POST; `/:id` PATCH (fields, `skills` as the whole list, close, reopen; company members and admins) and DELETE (only a job with no applications, else 409); `/:id/apply`; `/:id/applications` (ranked; the job's `skills` once, and per applicant `heldSkillIds` and `learningSkillIds`); `/applications/:id` (stage and private note). An application link is stored as https; one typed without a scheme gets it
- `/api/employer/*` memberships and the employer dashboard; `companies?q=` (find a company by name); `company-requests` GET, POST, DELETE `/:id` (ask for a missing company or factory). `/api/auth/me` carries `hasCompanyRequest`; factories on `GET /api/employer` carry `address`
- `/api/admin/*` (signed-in admin): `overview`; `users` (`?q=`, paged), `users/:id` PATCH `{ isAdmin, name, email }` and DELETE; `users/:id/sign-out` POST; `users/:id/reset-link` POST; `memberships` GET, POST (add a person to a company), PATCH (`decision: 'approve' | 'decline' | 'remove' | 'reopen'`); `invites` GET, POST, `invites/past`, `invites/:id` DELETE; `paths?status=draft`; `companies?q=`, `companies/:id` PATCH `{ domain, featured }`; `company-requests` GET, PATCH `/:id` `{ decision: 'add', companyId? } | { decision: 'decline' }`; `records/:kind?q=`, `records/:kind/similar?name=`, `records/:kind/:id` (the editor's view, with `attached` counts and a career's `path`), `records/:kind/:id/merge` POST; `audit`; `quality`; `intake/sources`; `intake/review` GET and `intake/review/:match` POST `{ decision: 'same' | 'different' | 'skip', plantId? }` (`overview` carries `waitingMatches`); `postings` (each employer's board with its latest run) and `postings/places` GET, POST `{ source, placeKey, decision: 'point' | 'leave' | 'wait', plantId? }` (pointing is audited as a `factory` line, `postings pointed here`; leaving a place or letting it wait again as a `company` line); `plants/pairs?list=id|spot&state=&limit=&offset=`, `plants/pair?a=&b=`, `plants/:id/near?q=`, `plants/apart` POST `{ a, b, apart? }`
- Record writes (signed-in admin): `POST`, `PUT /:id`, `DELETE /:id` on `/api/companies`, `/api/factories`, `/api/occupations`, `/api/skills`, checked through `server/lib/writes.ts`. A `POST` that would repeat a record answers 409 with `existing: { id, name }` (a company by name in any letter case; a factory by company, name and state; a career by title; a skill by name). A factory needs `companyId`, `name`, `state` (a code from `shared/states.ts`), `latitude` and `longitude` as numbers, and takes `city` and `address`. A career's `onetCode` is text of up to 20 characters on `POST` as on `PUT` (400 otherwise), trimmed, an empty one stored as null. A skill needs `name`, `group` (a group's slug, which fixes its domain) and `level` (1, 2 or 3): a missing or unknown one answers 400 with `field`, before the duplicate check. `PUT /api/factories/:id` also takes the depth fields above; `PUT /api/companies/:id` takes `parentCompanyId` and `headquartersCity`, `headquartersState`, `headquartersCountry`
- A company's versions of careers (`server/routes/versions.ts`, mounted ahead of `/api/companies`, never cached): `GET /api/companies/:company/careers` and `/:occupationId` (public; `:company` is an id or, for a read, a slug; one version is a path ready to draw: `skills` each with level, group, domain, `added`, `order` and `makes: [{ id, name, runs }]`, plus `leftOut` and `jobs`), `POST { occupationId }` (409 with `existing`), `PUT /:occupationId { added?, leftOut?, makes? }` (each a whole list; one not sent stays; 400 with `field` when a left-out skill is not on the standard path, an added skill does not exist, or a make is not of a skill on the version's path) and `DELETE /:occupationId`. Writes take one of the company's active members or an admin (`canManageCompany`): the one place under `/api/companies` that is not an admin's alone. `GET /api/occupations/:id/versions` lists the companies with one; `versions` is also on `GET /api/occupations/:id` and `GET /api/companies/:id`, and `hasVersion` on `GET /api/jobs/:id`
- `PUT /api/occupations/:id/path { skills: [{ skillId }], replace?, status? }` sets a career's skills in bulk (admin): with `replace` the skills not listed leave the path, `status` is `draft` or `approved`, and a `stage` sent is not read
- `/api/occupations` lists civilian careers; `?military=1` lists the military ones and `?service=<key>` one service's (400 for an unknown key), and with either `search` also finds a career by its code. `/:id` carries `reachedBy` (the military careers that reach a civilian career) and `withinReach` (the civilian careers a military one reaches, each with the skills missing). `/api/search` takes `military=named`; its careers then carry `leads` and its companies `service`. `/api/skills/:id` carries `militaryOccupations`, and each skill of `/api/skills/taxonomy` its `militaryCareers`. `/api/companies/:id` carries `serviceCareers` for a service. `/api/explore/facets` carries `militaryCareerDomains` (each with its `services`). `/api/stats/counts` `skills` leaves out the skills only military careers use. `/api/me/careers/reach` rows carry `openJobs`; `POST /api/me/careers/:occupationId/held` and `/held/undo` are Profile's door. `POST /api/jobs`, `PUT /api/me/goals/:id` and `POST /api/companies/:company/careers` answer 400 for a military career; `/api/admin/paths` rows carry `service` and `code`
- A career's service: `/api/occupations` rows and `/:id` carry `service { id, name, slug, key } | null`, `code`, `codeSystem`, `kind` (the derived words) and `officialTitle`, all null for a civilian career; `/api/companies/:id` carries `service`; `PUT /api/occupations/:id` takes `service` (a key, or null), `code` and `officialTitle` (checked and audited like every field; the code system is the service's own), and the admin's career form sets them. `DELETE /api/companies/:id` answers 409 for a service with careers
- `PUT /api/occupations/:id` takes `home` (a domain's slug, or null) and `leadsTo` (up to three career ids, in order; 400 with `field: 'leadsTo'` and the chain in words when a link would close a ladder); `POST` takes an optional `home`. `server/lib/careers.ts` holds the ladder's rules

## Migrations

`scripts/migrate.mjs` applies the SQL files it lists (0010 onward) once each, under a lock, and skips when `DATABASE_URL` is unset. `npm run build` runs it only on Vercel's production build (`VERCEL_ENV=production`); a preview, local or CI build leaves the database alone, and `npm run db:migrate` applies migrations on purpose. (If Vercel does not expose `VERCEL_ENV`, the build migrates as it always did and says so in its log.) `npm run db:create` builds the schema in an empty database (0000-0009, which predate the runner and are applied by `scripts/create-db.mjs`, then the runner); `-- --sample` adds sample data. There is no Drizzle Kit: `server/db/schema.ts` is for queries only.

The list must stay in order (a unit check fails otherwise); it is ordered, not contiguous: there is no 0031 or 0032. New tables go in a new idempotent SQL file in `migrations/`, added to the list in that script, and mirrored in `server/db/schema.ts`. A generated migration is never edited once applied: a later change is a change to its JSON in `data/` and a new generated migration.

What the notable ones did:
- `0010_accounts_jobs.sql`: accounts, company memberships, jobs, applications, a person's skills and goals. `0015_invites.sql` adds `invites`; `0020_password_resets.sql` adds `password_resets`.
- `0011`, `0016`, `0018`: career paths, generated by `scripts/build-paths-sql.mjs` from `data/paths/`. `0012` and `0013`: a company's `domain` and `featured` flag, the columns and then the values from `data/companies/profiles.json`; `0014`: slugs; `0019`: descriptions from the same file.
- `0021_industry_careers.sql` adds and fills `industry_occupations`.
- `0022_data_cleanup.sql` is generated by `scripts/build-cleanup-sql.mjs` from `data/cleanup/2026-11-cleanup.json` (careers, skills and companies deleted, merged and renamed; factories moved or removed; a merged name is kept as an alias).
- `0023_remove_legacy.sql` drops what the product no longer has: Elements (`refs`), Schools, Programs and People with their junction and alias tables, the `states`, `industries` and `skill_categories` lookups, `skill_relations`, `entity_links`, the spreadsheet import's tables, and the columns `factories.state_id` and `skills.category_id`. `occupation_aliases` and `skill_aliases` are kept: they hold the names of merged careers and skills, for search and for later merges. A state is its two-letter code (`factories.state`, `shared/states.ts`); a company's industry is text on its own row, and so is `skills.category`, which is kept and not shown (see "Skills").
- `0024_email_notices.sql`: see "Email and notices". `0025_admin_upkeep.sql`: `audit_log` and `users.admin_since`.
- `0026_company_requests.sql` adds `company_requests`; `0027_career_aliases.sql` fills `occupation_aliases`.
- `0028_indexes_and_checks.sql` adds three foreign-key indexes and two value checks (a path's stage is 1 to 3; a job's pay runs low to high).
- `0029_remove_puerto_rico.sql` deletes Puerto Rico's factories and the companies that existed only there: the product is the 50 states and the District of Columbia (`shared/states.ts`).
- `0030_depth_and_provenance.sql` adds the depth columns on `factories` and `companies`, `company_state_headcounts`, the curated-source index on `external_references` and `load_log`.
- `0033_skills_catalogue.sql` adds `skills.how_learned` and `skills.tools` and applies the skills catalogue. `0034_account_purpose.sql` adds `users.purpose`.
- `0035_industries.sql` adds `industry_profiles` (one sentence per industry) and `industry_stats`; `0036_industry_stats.sql` is generated from `data/industries/`.
- `0037_company_domains.sql` is generated by `scripts/build-domains-sql.mjs` from `data/companies/domains.json`: it sets `domain` only where it is empty, by exact name, and the file's `skipped` list says which companies were left out and why. `0045_company_domains_2.sql` is generated from `data/companies/domains-2.json` the same way: domains for companies that stand in the first ten of a list and had none.
- `0038_remove_construction_materials.sql` removes concrete and asphalt paving factories. As first applied to production it matched the whole cement-and-concrete group (NAICS 3273) and took the cement factories too; `0039_restore_cement_plants.sql` puts 41 cement factories and their companies back, and 0038 now names only the concrete codes.
- `0040_texas_employers.sql` and `0041_largest_plants.sql`: see "Depth and sources".
- `0042_skill_taxonomy.sql`: the taxonomy's tables and columns, every skill placed by name, and the two triggers (see "Skills"). It stops, changing nothing, when the stored skills are not exactly the ones the file places, so a skill an admin added, renamed, merged or deleted has to be brought into the catalogue and the taxonomy before a taxonomy migration will apply. `scripts/create-db.mjs` marks its first pass (`archangel.from_nothing`) so a database built from nothing is let through; its second pass, over the sample data, is checked like any other. A change to the taxonomy is a new numbered file (the builder's third argument is the output) that follows the catalogue's own new migration in the runner's list, and `tests/unit/taxonomy.unit.ts`, which names the latest, is pointed at it.
- `0048_skills_catalogue_2.sql`, `0049_skill_taxonomy_2.sql`: the catalogue pass (64 skills added, 51 folded, brand names and NDT course topics into the standard skill; 656 skills in 132 groups). `0050_skill_makes.sql`: `skill_makes`, `user_skill_makes` and the curated makes.
- `0043_intake.sql` adds the intake tables and functions, makes `external_references` the crosswalk, adds `record_merges` and `fact_sources`, and extends `load_log` (see "Intake").
- `0044_geo_keys.sql`: see "Geography and industry keys". Generated; a later year of county statistics is `node scripts/build-geo-sql.mjs --stats-only <file> --out <new migration>`.
- `0046_careers_catalogue.sql` and `0047_career_lists.sql`: see "Careers". Once applied to production, a change to the catalogue or its lists is a new generated migration (each builder's last argument is the output), and `tests/unit/careers.unit.ts`, which names both, is pointed at it.
- `0051_plant_duplicates.sql` is generated by `scripts/build-duplicates-sql.mjs` from `scripts/plant-merge.sql`, `scripts/employers-loader.sql` and `scripts/plant-duplicates.sql`. It adds the factory merge, then finds every outside id carried by more than one live factory and decides in SQL: rows that are certainly one factory and one company are merged (the same company row; the same name written differently; a recorded parent; one name beginning with the other's; or a factory named for one of the two companies, unless that would take it from a company with a profile to one without), the rest are left for a person (load `plant-duplicates`), and references to factories that no longer exist are removed. A second run changes nothing. `--rehearse` writes a run that undoes itself. A change to the rules is a change to `plant-duplicates.sql` and a new generated migration.
- `0052_career_paths.sql`: the path of every career, from `data/careers/paths.json` (see "Careers"). `0011`, `0016` and `0018` and `data/paths/` are the earlier paths, kept as history.
- `0053_company_careers.sql`: the three tables of a company's version of a career, no rows.
- `0054_job_postings.sql`: jobs from employers' postings (see "Job postings"): the columns on `jobs`, `job_makes`, `posting_places`, `posting_passes`, sources of kind `job`, the entity type `jobs`, and the functions. It loads no data. It stands in the list before 0056, which production had first; there is no 0055.
- `0059_skills_catalogue_4.sql`, `0060_skill_taxonomy_3.sql`: 66 skills in 11 new groups for the military careers (aircraft systems, engines and power plants, vehicles and heavy equipment, power generation and distribution, plant utilities, fielded electronic systems, weapons and munitions, survival equipment, shipfitting, nuclear plant operations, fuels and cryogenics); no stored skill renamed, moved or removed. `tests/unit/skills.unit.ts` and `taxonomy.unit.ts` name them. A skill no career uses yet is in the taxonomy and the Atlas (its panel says so) and is left out of the lists that count careers.
- `0061_career_service.sql`: what says a career belongs to a military service, with no rows: `companies.service` (`navy`, `army`, `air-force`, `marine-corps`; null for every other company; one company per service) and, on `occupations`, `service_company_id`, `code`, `code_system` (`navy-rating`, `army-mos`, `afsc`) and `official_title` (a career with a service has a code and a system, and a code is unique within its system). The words above the name ("Navy rating", "Army MOS", "Air Force specialty") and the tags are derived in `shared/military.ts`, never stored.
- `0062_military_employers.sql`: the four services as companies with no factories (U.S. Navy, U.S. Army, U.S. Air Force, U.S. Marine Corps), generated by `scripts/build-military-sql.mjs` from `data/careers/military/employers.json` (`--check` validates): a service is the company that already carries its key, else the one with exactly its name in any letter case, else a new one; only empty fields are filled; decisions in `load_log` (load `military-employers`). A service is left out of the Companies list, search and the counts (`browsableCompanyFilter`); its page is reached from a military career. Their marks are lettermarks on purpose: a service's emblem is an official insignia, not a company's logo (`logo-decisions.json`).
- `0063_military_careers.sql`, `0064_military_paths.sql`: the 118 military careers with their other names, and their paths as drafts (see "Military careers"); generated by `scripts/build-military-sql.mjs`, and `tests/unit/military.unit.ts` names them. No ladder link, industry or company version is written for one.
- `0056_career_lists_2.sql`, `0057_skills_catalogue_3.sql`, `0058_skill_makes_2.sql`: the names employers' postings use (32 other names of careers added and 11 taken back; 25 other names on 15 skills; nine makes on six skills). No career or skill is added. `tests/unit/careers.unit.ts`, `skills.unit.ts` and `makes.unit.ts` name them.

## Map

- All camera movement goes through `client/src/components/map/camera.ts`. Never call `flyTo`/`fitBounds` elsewhere, and never pass `padding` to `flyTo` (MapLibre saves it and `fitBounds` adds it again).
- Sources, layers and paint values live in `client/src/components/map/layers.ts`; what differs between the themes besides colour is its `LOOK` record. Dark is lights on a dark land: far out, factories are faint points under a density glow, and states are washed by how many factories they hold. Light is ink on white: every factory is a dot of `--text-1` at 70%, a fifth smaller, with no glow and no shading; US land is white (the `us-land` layer, the states' shapes under the basemap's water), other land `#f4f4f4`; the basemap keeps only water, roads and place names. In both, a selected state or focus area is outlined in `--accent` (light: 2px over a 6% fill), a hiring factory is ringed in it, and pins become pickable from about zoom 5.5 and sit beneath the place names.
- Everything floating over the map uses the one `.map-overlay` surface in `globals.css`: `--surface` with a `1px --line` border, solid, no shadow. Do not hand-roll another. Every control on the map takes the accent's focus ring (`.map-view :focus-visible`); the search field shows it on its box, and a row in a scrolling list (`.map-list-row`) and the canvas draw it just inside their edge.
- The panel has no boxes (`components/map/panel/parts.tsx`): figures are one row parted by upright hairlines (`Figures`), a list is rows the panel's width parted by hairlines (`ROW`, `RowList`), sections are parted by space, and names of sections and columns take `LABEL`.
- Hover cards render from the pin's own properties. No request on hover.
- With no `VITE_MAP_TOKEN`, or if the basemap fails, the map draws on a plain canvas in `--bg`.
- The attribution control stays (the basemap's and OpenStreetMap's terms require it), collapsed to its "i" button.
- Pins load once (`usePins` in `lib/queries.ts`); state, industry, company and career are filter and paint expressions set by `setPinView` in `layers.ts`. Never refetch or `setData` for a filter.
- What the panel shows for each kind of thing is a file in `components/map/panel/`.
- The map has at most one subject, a company (`?company=`, id or slug) or a career (`?career=`): `filters.company` / `filters.career` in `mapStore`. A company's factories are drawn alone and framed; a career's industries keep their strength and the rest step back. The chip under the search turns it off. A military career and a service are never the subject: such a link is answered like one that names nothing (`notFound()`).
- The map's address: `?factory= ?state= ?area= ?skill= ?place=&in=&box=` (what the panel shows), `?company= ?career=` (subject), `?industry=`; the camera is the fragment `#zoom/lat/lng`, written with replace by `MapView`. Something a link names that does not exist calls `notFound()`: one line beside the search, the country, the address cleaned.
- A click or tap selects after 250 ms unless a second one or a camera move cancels it (a double tap zooms). Touch reach is about 22 px close in and 10 px far out; states are hit at the exact point. Dragging is limited to `REACH` in `camera.ts`; flights made by `camera.ts` are exempt. Rotation and pitch are off.
- Map controls take their size from the pointer (`.map-control`, `.map-search-button`, `.map-row`, `.map-chip`, `.map-field` in `globals.css`): 44 px and 16 px type on `pointer: coarse`.
- The phone sheet rests at bar / peek / full (`sheetDetent`); the home view on a phone frames the country above the resting sheet.
- Map search lists states and focus areas, then the product's own companies, factories, careers and skills, then places (towns, counties, ZIP codes; streets only when the query has a digit) from `client/src/lib/geocode.ts`, under the shared search vocabulary (see "Routes"). It lists no industries or jobs: the map has no panel for either. A town opens a panel for its bounds: `GET /api/map/bounds/overview?west=&south=&east=&north=` (the region overview for any box, plus up to 24 factories).
- The map overviews list only the 21 as industries (`INDUSTRY_NAME_LIST` in `server/lib/industries.ts`), and the panels show them by their short names.
- A first visit is given one sentence under the search field, once per browser (`archangel.map.seen`), and only on the bare map: a link that opens a panel says what it is showing instead.

## Look and feel

The rule of thumb: it should look like software Tesla would ship on a vehicle screen, not like a consumer phone app.

- Monochrome and quiet, in both themes: a near-white or near-black page, one ink, one accent. No entity colours anywhere.
- Hierarchy comes from type, space and hairlines. A section is not a card; a list is rows with a hairline between them and no box; containment is one level deep at most (Explore's overview tiles are the only cards). No shadows, gradients or glass. A state is carried by ink, a mark or a line, never by a grey fill.
- Type is one scale: a page's title 40px / 600 (a job's keeps 24px on a phone, `longTitle`), a section heading 20px / 600, labels (field labels, eyebrows, column headings) 11 to 12px / 500 in small capitals and `--text-2`, body 15px, meta 13px in `--text-3`, numbers in lists and stats tabular. Text links are underlined.
- No stars, badges, emoji, counters or "click here" hints. Emphasis comes from order, size and brightness. Application stages and a skill's status read by brightness and shape, not hue; A confirmation is ink; `danger` is for errors and destructive actions. Section headings on entity pages carry no counts.
- Nothing on the map that the person did not ask for: no numbered bubbles, no labels on pins. Counts and detail live in the panel they open.
- Density reads naturally (dark: a glow far out; light: the dots themselves; distinct points close in), not as a chart.
- Motion is short and purposeful. Nothing flashes a loading state for content the client already has.

## Code Style

- TypeScript strict mode, no `any`
- Functional components with hooks
- Tailwind for styling
- Colours come from theme tokens only (see "Theme and colour")
- Type and states are written once in `lib/utils.ts`: `labelClass`, `pageTitleClass`, `sectionHeadingClass`, `segmentedClass` / `segmentClass`, `optionTileClass`; `rowHoverClass` is in `components/layout/Page.tsx`. `cardClass` adds nothing and is kept by name. Tailwind's `text-sm` is 15px (body) and `text-xs` 13px (meta). Buttons, inputs and option tiles are 8px at the corner; a primary button is the inverse pair, a secondary one a `--line-strong` hairline, a disabled one the same at 0.4. `CompanyLogo` is 32px in a list and 40px on Explore's cards, on a white backing with a 6px corner and a ring in dark only (a lettermark stays on `--surface`)
- List and account pages compose `PageContainer` / `PageHeader` / `PageSection` / `EmptyState` from `components/layout/Page.tsx`; detail pages compose the template in the same file (see "Detail pages"); primitives come from `components/ui/` (shadcn)
- Grids must set a mobile base (`grid-cols-1`) before breakpoint columns, and truncated children need `min-w-0`
- Env: `DATABASE_URL`, and the MapTiler key `VITE_MAP_TOKEN`; mail takes `RESEND_API_KEY`, `EMAIL_FROM` and `APP_URL` (see "Email and notices"). Locally they live in `.env.local` (copied from `.env.example`); the server reads `.env.local`, then `.env` (`server/loadEnv.ts`)
- The page and the API are one origin (Vercel rewrites `/api`; in dev Vite proxies it), so there is no CORS and the client always calls `/api`
- No service worker. The manifest is a static file (`client/public/manifest.webmanifest`); cache lifetimes are in `vercel.json`. The font (Oxanium) is bundled, not fetched from a third party
- Every route that takes `limit` or `offset` reads it through `pageLimit` / `pageOffset` (`server/lib/paging.ts`)
- In `server/lib/` each of these is written once: the rows of a hand-written statement, `rowsOf` (`rows.ts`); typed text inside a LIKE pattern, `likeLiteral` or `containing` (`like.ts`); "this job is open", `jobIsOpen()`, and the order jobs are listed in, `jobsInOrder()` (`openJobs.ts`); "may this person act for this company", `canManageCompany` (`auth.ts`); "this career is a civilian one", `civilianCareer()` and `civilianPathLine()` (`military.ts`); "is this an id", `isUuid` (`writes.ts`)
- `server/scripts/*.ts` run under tsx, may import from `server/` and `shared/`, and are type-checked but not linted. `scripts/*.mjs` are plain Node, import nothing from either, and run without a build (`migrate.mjs` runs inside Vercel's build)
- A new dependency is proven with a clean install (`npm ci` in a fresh copy, then `npm run build`), not with the packages already on disk: Vercel installs from the lockfile only
- A control that is saving is marked `aria-busy` / `aria-disabled` (`busyButtonClass`), never `disabled`: a disabled control drops keyboard focus. A form names each problem beside its field and focuses the first
- Requests to the API go through `request` in `lib/http.ts`, or for the reads in `lib/api.ts` its own `apiFetch`; both use `fetchWithTimeout` (`lib/http.ts`) and give up when no answer has begun in 20 seconds. Only static files and the geocoder are read with `fetch` itself. Mutations run with `networkMode: 'always'`: a change made offline fails there and then
- Every query key is in `lib/queryKeys.ts` (`accountKeys`, `publicKeys`); a new query adds its key there. A read several components make is declared once in `lib/queries.ts`: a record's page, the map's panel and a list row's prefetch all read it through `recordQuery`, so an admin's correction reaches them together
- Button groups acting as tabs or radios use `onGroupArrowKeys` (`lib/roving.ts`; `arrowKeyChoice` there is the same thing as a handler) with a roving tabindex; `SegmentedChoice` in `components/account/parts.tsx` is the control built on it
- After a deliberate sign-out a gated page sends the person to the map (`justLeft` in `lib/account.ts`)
- An entity page picks its view from the address (`entityType`), never from the shape of the response; the shape checks in `EntityDetail.tsx` only narrow types, and each view is a file in `components/entity/`. Adding a field to a response must not be able to change which page is drawn
- Server/api relative imports MUST end in `.js` (`from './routes/map.js'`, `from '../db/index.js'`): the function runs as Node ESM on Vercel. `npm run lint` enforces it
- Browser storage is read and written only through `client/src/lib/storage.ts`, which never throws. The one exception is the theme script in `client/index.html`, which runs before any module
- A company's logo comes from `client/public/logos/` when `client/src/lib/logos.json` lists its domain (null means lettermark, no request); only a domain not in the list still asks the favicon service. `scripts/fetch-logos.mjs` fills both from every domain the data names and is safe to run again; decisions made by hand are kept in `data/companies/logo-decisions.json` (`README.md`, Logos, has the sources it tries and the steps). Look at every new mark (`--sheet out.html`) before committing: a wrong logo is worse than a letter. The 2 to 1 limit is for unattended runs; by hand (`--look` shows every mark on offer, `--place` keeps one) a company's own square icon, the symbol cut from its logo, or a short bold wordmark that reads at 28 px is right. Every company in the first ten of a list has a mark or a reason in `logo-decisions.json`. The script says what it is in every request and leaves a site that refuses alone
- The page's Content-Security-Policy is in `vercel.json`; a new outside host must be added there, and an inline script in `client/index.html` by its hash (`npm run lint` checks)
- Deleting a company, factory or career is refused (409) when one of its jobs has applications: such a job is closed, never deleted. Jobs nobody applied to go with the record, and the confirmation says so
